# ML/NLP: подход и обоснование порогов

## Классификация темы обращения

В PoC используется пайплайн `TF-IDF (word, n-grams 1-2) + Decision Tree`, обученный на вопросах из базы знаний плюс несколько синтетических примеров для тем "complaint" и "abuse" (их нет в базе знаний). Это осознанно простое решение для демонстрации логики пайплайна, а не production-модель.

Темы: `account_access`, `billing`, `technical_issue`, `general_question`, `complaint`, `abuse`.

"Рискованные" темы (`RISKY_TOPICS = {complaint, abuse, billing}`) всегда уходят на ручную проверку оператором независимо от уверенности классификатора — ошибка в этих темах дороже, чем лишняя эскалация.

В продакшене классификатор нужно переобучить на реальных исторических тикетах (тысячи примеров, а не десятки), рассмотреть более мощную модель (градиентный бустинг на эмбеддингах или дообученный трансформер) и вести мониторинг дрейфа данных.

## Пороги уверенности (confidence thresholds)

```
CONFIDENCE_AUTO    = 0.75   # >= этого значения -> можно автоматически закрывать тикет
CONFIDENCE_SUGGEST = 0.50   # >= этого значения -> предложить черновик оператору
                             # ниже -> эскалация без черновика (модель "не уверена")
```

Обоснование:
- Порог 0.75 для авто-закрытия выбран консервативно: ошибочное авто-закрытие тикета (когда клиенту дан неверный ответ без проверки человеком) наносит больше вреда, чем лишняя ручная проверка. Это тот порог, который в реальном проекте должен калиброваться на исторических данных по цене ошибки (FP/FN) для каждой темы.
- Порог 0.50 для suggest — это медиана между "случайным угадыванием" (для 6 классов ~0.17) и порогом авто-закрытия; ниже него модель фактически не увереннее, чем в случайном классе, и черновик, скорее всего, будет бесполезен или вреден оператору.
- Оба порога — гиперпараметры системы, а не догма; их нужно тюнить по метрикам качества (см. `monitoring.md`) отдельно для каждой темы, так как цена ошибки в `billing` и в `general_question` разная.

## Поиск по базе знаний (retrieval)

PoC использует косинусное сходство по TF-IDF векторам между текстом тикета и вопросами из `knowledge_base.json`. Это быстро, не требует внешних сервисов и достаточно для демонстрации, но плохо обобщается на перефразированные вопросы и синонимы.

Целевая архитектура: sentence-embeddings (например, мультиязычная модель для русского) + векторная БД (pgvector или FAISS) для семантического поиска по большой базе знаний, с возможностью инкрементального обновления индекса.

## PII/PD-детекция

В PoC `pii.py` использует регулярные выражения и эвристики для поиска признаков персональных данных (номера телефонов, email, паспортные данные, номера карт и т.д.) и оценивает уровень риска по совокупности сигналов, а не по одному признаку (например, одно упоминание имени само по себе не поднимает риск до максимума, а комбинация имя + телефон + адрес — поднимает). Это осознанное решение, чтобы не эскалировать избыточно много обычных обращений.

В продакшене вместо регулярок нужен полноценный сервис PII/NER (например, на основе NER-модели, обученной под специфику домена и русского языка), а также юридическая консультация по тому, какие типы данных считать чувствительными в контексте 152-ФЗ.

## Метрика уверенности

`confidence` — это максимальная апостериорная вероятность класса из `predict_proba()` дерева решений. Это простая, но грубая метрика уверенности (деревья решений склонны быть "самоуверенными"); в продакшене стоит использовать калиброванные вероятности (Platt scaling / isotonic regression) или температурное масштабирование для LLM-классификаторов.
