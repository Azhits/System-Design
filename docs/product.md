# Продуктовый расчёт и бизнес-обоснование

## Задача

Снизить нагрузку на операторов поддержки, ускорить первый ответ по типовым обращениям и точнее маршрутизировать сложные случаи — без ухудшения CSAT и без роста reopen rate.

## Исходные данные (из условия задачи)

| Параметр | Значение |
|----------|----------|
| Тикетов в день | ~200 000 |
| Стоимость ручной обработки | 150 ₽/тикет (~8 мин) |
| SLA первого ответа | 15 минут |
| Текущий CSAT | 4,2 / 5 |
| Текущий reopen rate | 9% |
| Доля типовых тикетов | ~40% (~80 000/день) |
| Пиковая нагрузка | до 10–20k тикетов за 10 минут |

## Допущения (явные assumptions)

- Из 40% типовых тикетов система сможет безопасно авто-закрыть **30–40%** (консервативная оценка с учётом ошибок классификатора и PII-фильтрации).
- Стоимость LLM-инференса на один тикет (только для safe-путей): ~1–2 ₽ при среднем черновике ~500 токенов.
- Стоимость поддержки системы (инфра + ML-инженер): ~500k ₽/мес (assumption).
- Автоматизация не применяется к billing, complaint, abuse, high-PII — только suggest для оператора.
- Suggest-режим сокращает время обработки оператором на ~50% (с 8 до ~4 мин) для тикетов с черновиком.

## Расчёт экономического эффекта

### Прямая экономия (auto_close)

```
Целевой auto_close: 30% от 80k типовых = 24 000 тикетов/день
Экономия: 24 000 × 150 ₽ = 3 600 000 ₽/день
Минус стоимость LLM: 24 000 × 1,5 ₽ ≈ 36 000 ₽/день
Чистая экономия: ~3 564 000 ₽/день ≈ ~106 млн ₽/мес
```

### Косвенная экономия (suggest-режим для операторов)

```
Тикеты с черновиком (suggest): ~20% от 200k = 40 000 тикетов/день
Сокращение времени оператора: с 8 до 4 мин = -50%
Экономия: 40 000 × 75 ₽ = 3 000 000 ₽/день
```

### Итого потенциальная экономия

| Статья | ₽/день | ₽/мес |
|--------|--------|-------|
| auto_close (прямая) | 3 564 000 | ~107 млн |
| suggest (косвенная) | 3 000 000 | ~90 млн |
| **Итого до затрат** | **6 564 000** | **~197 млн** |
| Стоимость LLM | −36 000 | ~1 млн |
| Стоимость системы (инфра + ML) | — | ~0,5 млн |
| **Чистая экономия** | **~6 528 000** | **~196 млн** |

> ⚠️ Это расчёт при целевых показателях качества. На старте пилота автоматизацию стоит ограничить suggest-режимом без авто-закрытия.

## Влияние на продуктовые метрики

| Метрика | До | Цель | Триггер стоп |
|---------|-----|------|-------------|
| CSAT | 4,2/5 | ≥ 4,2/5 | < 4,0 на авт. тикетах |
| Reopen rate | 9% | ≤ 9% | > 12% устойчиво |
| SLA первого ответа (типовые) | 15 мин | < 2 мин | > 15 мин |
| Auto-close rate | 0% | 30–40% | < 10% (система не работает) |
| Operator draft acceptance rate | — | ≥ 60% | < 30% (черновики бесполезны) |
| Стоимость LLM/тикет | — | < 2 ₽ | > 5 ₽ (ROI теряется) |

## Сценарии запуска (go-live strategy)

### Этап 1 — Shadow mode (неделя 1–2)
Система обрабатывает все тикеты параллельно, но решения не применяются. Цель: оценить распределение классов, точность PII-детекции, latency.

### Этап 2 — Suggest only (неделя 3–6)
Система предлагает черновики операторам, авто-закрытия нет. Собираем operator feedback (принят / отредактирован / отклонён). Цель: убедиться в качестве черновиков (acceptance ≥ 60%) и отсутствии роста reopen rate.

### Этап 3 — Selective auto-close (неделя 7+)
Авто-закрытие только для `account_access` + `general_question` при confidence ≥ 0.85. Постепенно расширяем по мере накопления данных.

## Когда остановить проект (go/no-go критерии)

Остановить пилот или откатиться к suggest-only, если:
- CSAT на авто-закрытых тикетах < 4,0 устойчиво в течение 3 дней;
- reopen rate на авто-закрытых тикетах > 12% (в 1,33× от текущего);
- operator draft acceptance rate < 30% (черновики не помогают, только мешают);
- стоимость LLM-инференса > 5 ₽/тикет (ROI становится отрицательным);
- доля ошибочной маршрутизации risky-тикетов (billing/complaint/high-PII) в auto_close > 0,1%.

## Нефинансовая ценность

- **Скорость**: типовые тикеты закрываются за секунды вместо 15 минут → рост CSAT.
- **Стабильность при пиках**: система деградирует, но не падает — оператор не получает волну тикетов без контекста.
- **Аудируемость**: каждое решение имеет decision_trace → снижение юридических рисков.
- **Масштабируемость**: при росте пользователей операционные расходы растут медленнее объёма.
