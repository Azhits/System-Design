# Риски и операционные вопросы

## Highload и надёжность

- **Разделение синхронного и асинхронного путей.** Приём тикета, детекция PII, классификация темы и принятие решения о маршрутизации — строго синхронный путь, целевой ориентир ≤ 500 мс. Генерация черновика через LLM вынесена в асинхронный контур и не блокирует ответ пользователю. Это критично при пиковом потоке 10–20k тикетов за 10 минут: синхронный путь должен справляться при нагрузке ~33 req/s в пике без участия LLM.

- **Управляемая деградация при нагрузке (L0–L4).** При росте queue_size система автоматически снижает использование LLM: L1 (50–199) — micro-batching, L2 (200–499) — только retrieval-шаблоны, L3 (500+, или LLM недоступен) — retrieval без LLM, L4 (10 000+) — прямая маршрутизация оператору без черновика. Это позволяет продолжать обработку при инцидентах, когда поток возрастает в 5–10× от нормального, не создавая очередь блокирующих LLM-вызовов.

- **Circuit breaker для внешнего LLM.** Все вызовы LLM API обёрнуты в circuit breaker с backoff и timeout. При недоступности провайдера система мгновенно переключается в retrieval-fallback (L3) без влияния на синхронный путь классификации. Retry не делаются на горячем пути — только в асинхронной очереди, чтобы не накапливать latency при деградации провайдера.

- **Audit log для всех решений.** Каждый тикет фиксируется в `logs/decisions.jsonl` с полями: `ticket_id`, тема, confidence, PII-риск, выбранное действие, уровень деградации, `decision_trace`, latency_ms, версия модели. В production — централизованное хранилище с retention-политикой. Это критично как для расследования инцидентов, так и для offline-анализа качества системы.

## Privacy, safety и risk

- **PII-детекция и маскирование перед LLM.** Перед любым вызовом внешнего LLM выполняется маскирование: номера карт, паспортные данные, СНИЛС — всегда `high_pii` и никогда не передаются в LLM. Сочетание ФИО + телефон/email/адрес также переводит тикет в `high_pii`. Одиночные слабые сигналы (только имя, только email) — `low_pii`, маскируются перед отправкой. В PoC реализовано через regex; в production необходим NER-сервис с тонкой настройкой под домен и 152-ФЗ / GDPR.

- **Категории, которые нельзя автоматически закрывать.** `billing`, `complaint`, `abuse` всегда уходят оператору — независимо от confidence классификатора. `high_pii` — только retrieval-черновик + escalation; повторная LLM-обработка допустима только после явного подтверждения оператором (human-in-the-loop, смоделировано в UI кнопкой «Оператор подтвердил безопасность»). Low-confidence (< 0.50) тоже не закрываются автоматически. Это защищает от ошибочных решений в сценариях с высокой ценой ошибки: финансовые претензии, юридически чувствительные обращения, возвраты.

- **Защита от prompt injection.** Пользовательский текст не интерпретируется как инструкция. В LLM-контур передаётся нормализованный и частично санитизированный текст; системный prompt жёстко отделён от пользовательского контента; LLM ограничен ролью «предложить черновик ответа» и не имеет доступа к внешним операциям или изменению состояния систем. Высокорисковые тикеты (high_pii) не передаются в LLM вообще.

- **Аудируемость каждого решения.** В record каждого тикета сохраняется `decision_trace` — список причин: какие PII-сигналы сработали, почему выбран именно этот уровень деградации, какой KB-фрагмент использован, была ли LLM или retrieval-fallback. Это позволяет ответить на вопрос «почему система приняла это решение» для любого тикета в любой момент — критично для compliance и разбора жалоб.
